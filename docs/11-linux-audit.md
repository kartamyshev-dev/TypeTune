# Аудит Linux input backend

Дата: **2026-09-10**. Baseline исходников: **`8cc19d0`**. Статус: анализ, runtime в рамках этой работы не исправлялся.

## Вывод и границы проверки

Текущая реализация нарушает базовый контракт клавиатурного транспорта ещё до корректора и сниппетов: меняет физические keycode, трактует autorepeat как отпускание и не связывает остановку с циклом чтения. Поэтому проблему нельзя свести к раскладке конкретного Linux-дистрибутива. Даже отключение всех текстовых функций не превращает демон в корректный прозрачный фильтр.

Аудит выполнен по исходникам на macOS. **Live-проверок Linux, EVIOCGRAB, uinput, X11, Wayland, настоящего hotplug и восстановления клавиатуры не было.** Доказанные дефекты ниже означают установленный путь исполнения и/или локальный детерминированный эксперимент; это не заявление, что наблюдался соответствующий сбой на компьютере пользователя. Риски, зависящие от desktop, драйвера или момента сбоя, отмечены отдельно.

Приоритеты:

- **P0** — блокирует испытания с основной клавиатурой и выпуск: повреждение ввода либо отсутствие управляемого выхода из перехвата.
- **P1** — нарушает обязательный контракт backend или функции.
- **P2** — долг реализации, диагностики и переносимости.

Связанные документы: [аудит функций](12-feature-audit.md), [целевая архитектура](13-target-architecture.md), [план разработки и проверки](14-development-plan.md).

## Какой код действительно исполняется

`typetune-input/src/lib.rs` содержит активные `EvdevDevice` и `EvdevSource`; `typetune-cli/src/main.rs:15` импортирует `typetune_input::EvdevSource`. Файл `typetune-input/src/evdev_source.rs` не объявлен через `mod` и в сборку не входит. В нём есть другая реализация преобразования keycode и grab. Исправление только этого файла не изменит поведение демона.

Фактический путь:

```text
одноразовый scan /dev/input/event*
  → открыть устройства
  → создать одну общую виртуальную клавиатуру
  → EVIOCGRAB
  → epoll + raw read(input_event)
  → оставить только EV_KEY, преобразовать code/value
  → InputEvent::new(...), character=None, timestamp=Instant::now()
  → AntiChatter → LayoutCorrector → SnippetExpander
  → write /dev/uinput + SYN_REPORT для каждого события
```

`LayoutManager` присутствует в зависимости CLI, но не создаётся и не вызывается. Чтение конфигурации X11/Wayland, получение фактической раскладки и декодирование текста в этом пути отсутствуют.

## Подтверждённые дефекты

### L01 · P0 · evdev keycode повреждается до pipeline

**Код:** `crates/typetune-input/src/lib.rs:85–94`, особенно строка 92; `crates/typetune-inject/src/lib.rs:118–124`.

Из native Linux code вычитается `EVDEV_OFFSET=8`. Результат затем без обратного преобразования отправляется в uinput. evdev и uinput используют Linux keycode; XKB offset относится к отдельной границе декодирования, а не к этому транспортному пути. Внутри `LayoutManager` уже предусмотрено добавление 8 (`typetune-layout/src/lib.rs:35,44`).

Трасса без корректора и сниппетов:

| Физический input | После `read_events` | Отправка uinput | Результат на уровне клавиш |
| --- | --- | --- | --- |
| `KEY_A=30, value=1` | `22, Pressed` | `KEY_U=22, value=1` | A превращается в U |
| `KEY_LEFTSHIFT=42, value=1` | `34, Pressed` | `KEY_G=34, value=1` | модификатор превращается в G |
| `KEY_ENTER=28, value=1` | `20, Pressed` | `KEY_T=20, value=1` | Enter превращается в T |
| `KEY_ESC=1, value=1` | `1u32 - 8` | зависит от overflow checks | panic при включённой проверке; wrapping и неверный `u16` при выключенной |

То же переполнение затрагивает коды `KEY_1`–`KEY_6`. Это не настройка раскладки: меняется сама физическая клавиша. Режим `enabled=false` сохраняет дефект, поскольку отключает только pipeline после ошибочного преобразования (`typetune-cli/src/main.rs:250–255`).

**Требуемый контракт:** raw Linux `code` проходит через физический backend без offset; типы `LinuxKeyCode`, XKB keycode и платформенный native code не взаимозаменяемы. Набор контрактных тестов должен включать как минимум Esc, цифры, буквы, все левые/правые модификаторы, навигацию и доступные media keys.

### L02 · P0 · autorepeat превращается в KeyUp

**Код:** `crates/typetune-input/src/lib.rs:86–90`; `crates/typetune-core/src/event.rs:3–7`.

Активный reader считает нажатиями только `value=1`, а все остальные значения — отпусканиями. Модель ядра вообще не имеет `Repeat`. Для удерживаемой клавиши последовательность `1,2,2,0` становится `Pressed,Released,Released,Released`. Первый autorepeat преждевременно снимает нажатое состояние виртуальной клавиши.

Linux определяет `0` как отпускание, `1` как нажатие, `2` как повтор. `SYN_REPORT` задаёт границы пакета; после `SYN_DROPPED` требуется восстановить состояние. Это подтверждено [спецификацией Linux input events](https://docs.kernel.org/input/event-codes.html#ev-key).

**Требуемый контракт:** `Down`, `Up`, `Repeat` — разные состояния; backend явно определяет, откуда берётся repeat для каждой среды. Нельзя одновременно воспроизводить аппаратные повторы и оставлять неконтролируемый второй генератор. Повтор не должен ни снимать удержание, ни заново переключать Caps Lock, ни считаться chatter-нажатием.

### L03 · P0 · явный ungrab вызывает grab

**Код:** `crates/typetune-input/src/lib.rs:40–56`.

`grab()` и `ungrab()` передают в `EVIOCGRAB` указатель `&grab_val`. Для этого ioctl важен сам нулевой/ненулевой аргумент, а не число по адресу. Поэтому адрес переменной со значением 0 в `ungrab()` всё равно запрашивает grab. Возвращённая ошибка игнорируется.

Это проверено по [Linux v6.12, `evdev.c`, строки 1084–1088](https://github.com/torvalds/linux/blob/v6.12/drivers/input/evdev.c#L1084): ветка выбирается по `if (p)`. Дополнительная локальная сверка установленной зависимости `evdev 0.13.2`: `raw_stream.rs:648,658` передаёт integer `1/0`, а `sys.rs:74` объявляет `ioctl_write_int!`.

**Практический предел вывода:** при закрытии владеющего fd grab освобождается ядром, поэтому это не утверждение о вечной блокировке после завершения процесса. Но `ungrab_all()` само по себе не выполняет обещанное освобождение. Более того, попытка «ungrab» ранее незахваченного открытого устройства способна запросить новый grab.

**Требуемый контракт:** один RAII-владелец устройства, отслеживание grab-state, проверяемое освобождение через библиотечный API, отдельный тест «ungrab, пока объект и fd ещё живы». Проверка только после выхода процесса не обнаружит этот дефект.

### L04 · P0 · SIGINT и SIGTERM не останавливают event loop

**Код:** `crates/typetune-cli/src/main.rs:126–129`; `crates/typetune-input/src/lib.rs:138–140,170–171,196–198,248–250`; CLI stop — строки 299–312.

CLI регистрирует сигналы на `Arc<AtomicBool>`, изначально равный `true`, и больше его не читает. `signal-hook::flag::register` при сигнале записывает `true` — это подтверждено локальным исходником зафиксированной зависимости `signal-hook 0.3.18`, `src/flag.rs:153–158`. Reader хранит собственный, другой `Arc`, тоже выставляет его в `true` и проверяет только его. `EvdevSource::stop()` из CLI не вызывается.

Трасса: `typetune stop` → SIGTERM → запись `true` в неиспользуемый флаг → epoll продолжает работу → через 5 секунд клиент печатает предупреждение. Флаг не только не связан с циклом, но и имеет неверную для текущей проверки полярность.

**Требуемый контракт:** единый источник shutdown-события для worker/backend; сигнал будит poll; контролируемое завершение отпускает захваченные устройства и уничтожает виртуальные. Испытания SIGINT/SIGTERM проводятся отдельно от аварийного завершения процесса.

### L05 · P0 · ошибка инжекции оставляет физические устройства захваченными

**Код:** `crates/typetune-cli/src/main.rs:250–262`; `crates/typetune-core/src/pipeline.rs:3–6`; `crates/typetune-input/src/lib.rs:163`.

Ошибка `vkb.emit()` только логируется, обработка продолжается. Callback имеет тип `Fn(InputEvent)` без результата; вернуть ошибку в цикл ввода и потребовать освобождения устройств невозможно через его контракт. У потребителя нет гарантированного рабочего пути ввода после отказа output.

**Подтверждено:** отсутствие перехода в восстановление по ошибке записи. **Условный результат:** потеря последующего ввода при реально отказавшем uinput; этот отказ в Linux не инжектировался.

**Требуемый контракт:** ошибка output — событие управления с причиной и стадией частичного выполнения; новые текстовые операции запрещаются, состояния удержаний сверяются, владелец grab обязан завершить перехват по ограниченному сроку. Внешний supervisor должен уметь завершить зависший процесс-владелец fd: обработчик внутри того же заблокированного callback не является watchdog.

### L06 · P1 · утрачены время, источник, границы пакета и пересинхронизация

**Код:** `crates/typetune-input/src/lib.rs:59–99,109–112,216–220`; `crates/typetune-core/src/event.rs:10–24`.

`input_event.time` отбрасывается; timestamp создаётся после чтения в момент вызова callback. Отбрасываются `EV_SYN`, включая `SYN_DROPPED`. `InputEvent` не содержит device/seat, поколения подключения, native type/value, sequence или признака потери синхронизации. `read_events()` дочитывает устройство до `EWOULDBLOCK` и только затем передаёт весь накопленный список.

Последствия, следующие из модели:

- Два настоящих нажатия с большим интервалом, прочитанные одним накопившимся batch после задержки процесса, получают почти одинаковые `Instant`; AntiChatter может подавить второе как быстрое.
- Нет возможности разделять дребезг одной клавиатуры и нажатие той же клавиши на другой.
- При потере событий программа продолжает работать с недостоверной историей удержаний.
- При чтении нескольких устройств порядок задаётся обходом готовых fd и их batch, а не явно определённым порядком событий с временными метками.
- Если после уже прочитанных событий следующий raw read вернул ошибку, метод возвращает `Err`, и локально накопленный `Vec` не доставляется.

**Требуемый контракт:** сохранять monotonic source time и отдельное receive time, device/seat identity, последовательность и native frame. Смена clock domain должна быть явной. `SYN_DROPPED` переводит устройство в resync; текстовый контекст инвалидируется до завершения сверки. Предпочтителен существующий синхронизирующий evdev API вместо ручного reader без этого протокола.

### L07 · P1 · hotplug реализован только как удаление fd из epoll

**Код:** `crates/typetune-cli/src/main.rs:165–175`; `crates/typetune-input/src/lib.rs:223–236`; `crates/typetune-input/src/device_discovery.rs:4–37`.

Устройства ищутся один раз. `udev` есть в зависимостях, но монитор добавления/удаления не создаётся. После `ENODEV` fd удаляется из epoll; `EvdevDevice` остаётся в `devices`. Новую клавиатуру или переподключённую Bluetooth/USB-клавиатуру демон не подхватывает. Если исчезли все устройства, loop продолжает ожидание без смены статуса.

Нет owned pressed-set, поэтому backend не может снять в виртуальном устройстве клавиши, удерживавшиеся отключённым источником. Реальное «залипание» зависит от трассы; отсутствие механизма восстановления доказано статически.

**Требуемый контракт:** события add/remove/change, стабильная identity плюс generation, отдельное удаление состояния устройства, повторное получение capabilities/доступа на reconnect. Path `eventN` не является постоянной identity. Статус «работает без клавиатур» должен отличаться от ready. Нельзя повторно захватывать собственное виртуальное устройство.

### L08 · P1 · один общий output не учитывает владельцев удержаний

**Код:** `crates/typetune-cli/src/main.rs:230–237`; `crates/typetune-core/src/event.rs:10–15`; `crates/typetune-inject/src/lib.rs:118–124`.

Несколько источников сводятся в один `VirtualKeyboard` без информации, кто удерживает клавишу. Трасса после исправления L01: `D1 Shift↓`, `D2 Shift↓`, `D1 Shift↑`, пока D2 удерживается. Текущее представление передаёт последний Up в общий output, хотя у клавиши ещё есть физический владелец. AntiChatter дополнительно может подавить D2 Down.

**Требуемый контракт:** выбрать и задокументировать либо виртуальное устройство на физический источник, либо корректный агрегатор удержаний по владельцам. Synthetic action тоже является отдельным владельцем; её завершение не должно отпускать физически удерживаемый Shift/Ctrl. Disconnect снимает только удержания отключённого owner.

### L09 · P1 · AntiChatter не является полноценным debounce состояния

**Код:** `crates/typetune-chatter/src/lib.rs:15,28–33,71–94`.

Фильтр сравнивает только времена принятых Down. Все Up всегда проходят. Отсутствуют состояния physical/logical down, отложенный release, таймер и device identity; Right Meta отсутствует в списке модификаторов. Это отдельный дефект алгоритма, который останется после исправления смещения кодов.

На macOS выполнен временный probe, импортирующий фактические `typetune-core` и `typetune-chatter`; timestamps задавались детерминированно. Конфигурация `debounce_ms=50`, `modifier_debounce_ms=30`, keycode 30:

| Вход `(ms,state)` | Фактический выход | Что установлено |
| --- | --- | --- |
| `0↓,10↑,15↓,20↑` | `0↓,10↑,20↑` | у подавленного Down его Up остаётся; поток логических переходов не сбалансирован |
| `0↓,1000↑,1005↓,1010↑` | все 4 события | дребезг при отпускании после долгого удержания не фильтруется |
| `D1:0↓,D2:20↓,D1:30↑,D2:70↑` после утраты identity | `0↓,30↑,70↑` | чужое нажатие той же клавиши ошибочно подавляется |

Вторая трасса важна: длительность предыдущего удержания не должна решать, является ли отскок через 5 ms самостоятельным нажатием. Третья проверяет контракт входа: библиотека уже не получает D1/D2 и не способна отличить эти события.

**Требуемый контракт:** отдельная per-device/per-key state machine; timer-driven решение для release bounce; ownership физического и уже доставленного состояния; независимая обработка repeat. Политика задержек, поведение быстрых намеренных повторов и модификаторов выбираются по записанным трассам и проверяемой допустимой задержке. Число «50 ms» само по себе не доказывает отсутствие потери быстрого набора.

### L10 · P1 · layout bridge отсутствует, существующий decoder не отражает desktop

**Код:** `crates/typetune-layout/src/lib.rs:22–26,34–55`; `crates/typetune-cli/src/main.rs:185–219,250–262`; `crates/typetune-core/src/event.rs:22–23`.

Все реальные события создаются с `character=None`; вызовов `with_character`/`LayoutManager::new` вне определений нет. Поэтому обычные слова не попадают в текстовую ветку корректора. Зависимость на XKB не делает связку реализованной.

Даже если подключить текущий `LayoutManager`, он компилирует собственную постоянную `us,ru` keymap, начинает с нового пустого state и не читает раскладку/модификаторы desktop. `key_get_utf8(...).chars().next()` сохраняет только первый scalar. `current_layout()` проверяет строку `"ru"`, хотя имя XKB group и RMLVO layout identifier — разные сущности; конкретный результат этого сравнения на Linux необходимо проверить, а затем работать с индексом/идентичностью реальной keymap.

Официальный [libxkbcommon Quick Guide](https://xkbcommon.org/doc/current/md_doc_2quick-guide.html) разделяет получение keymap и state для evdev, X11 и Wayland; локальная keymap не является автоматическим отражением оконной системы.

**Требуемый контракт:** origin/epoch keymap, источник достоверного state, формат текста `String`, compose/IME state и степень достоверности наблюдения. Native input, интерпретация клавиши и подтверждённый текст должны быть разными типами событий. Нельзя исправлять это только вызовом `keycode_to_char` для всех Down/Up: release не вводит символ, а shortcut/IME не равны обычному набору.

### L11 · P1/P2 · виртуальное устройство и discovery не обеспечивают прозрачность

**Код:** `crates/typetune-inject/src/lib.rs:49–89,95–125`; `crates/typetune-input/src/device_discovery.rs:40–86`.

Подтверждённые ограничения реализации:

- Output объявляет только `EV_KEY` и keycode `0..255`; возможности найденных устройств не сопоставляются с output. Расширенные клавиши вне диапазона не поддержаны, даже если source их имеет.
- Native frames распадаются на отдельные события с отдельными `SYN_REPORT`; поведение unsupported event types не определено. Обратной передачи LED/lock feedback нет.
- Создание uinput считается готовностью к перехвату; нет проверки, что desktop уже подключил виртуальную клавиатуру. Потеря первых событий при такой гонке — риск, не наблюдённый факт.
- Raw write проверяет только `<0`, не обрабатывает короткую запись/повтор после interruption и не сообщает errno; fd output не открыт с `O_CLOEXEC`.
- Discovery скрывает причины недоступности устройств и использует эвристики по имени. Строка `"g pro"` исключает любое совпадение, в том числе имя клавиатуры, если оно содержит эту подстроку. Устройства с объединёнными keyboard/pointer capabilities полностью исключаются.

Документация ядра рекомендует библиотечную обёртку для нового кода, описывает readiness-гонку при появлении uinput и относит используемый здесь `uinput_user_dev` к старому интерфейсу. Сам старый интерфейс ещё не доказывает неработоспособность; проблема в неполном контракте и ручной обработке ошибок. [Linux uinput](https://docs.kernel.org/input/uinput.html).

**Требуемый контракт:** явная политика supported capabilities и объяснимые причины отказа для каждого устройства; allow/deny по identity/capabilities; output-ready до grab; feature negotiation для feedback и дополнительных кодов. Неподдерживаемое комбинированное устройство безопаснее оставить вне перехвата и показать причину, чем незаметно повредить его функции.

## Что следует изменить в подходе

### Разделить физическую фильтрацию и работу с текстом

Anti-chatter обязан видеть физическое устройство, полную последовательность Down/Up/Repeat и source timestamps. Текстовый корректор обязан знать раскладку, контекст поля, состояние ввода и результат вставки. Одна функция `InputEvent -> Vec<InputEvent>` смешивает эти задачи и не несёт данных, необходимых ни для надёжной фильтрации, ни для безопасной замены текста.

Для Linux следует предусмотреть независимые возможности backend:

| Возможность | Что подтверждает ready | Что нельзя выводить из неё |
| --- | --- | --- |
| Наблюдение native keyboard | доступ к источнику и корректные события | наличие Unicode или разрешение подавлять оригинал |
| Подавление физического ввода | проверенный grab и путь освобождения | доступ к активному приложению или IME |
| Получение layout/state | конкретный источник keymap + state, обработка смены | право выполнять глобальные замены |
| Вставка текста | выбранная стратегия, Unicode, результат и ограничения | что приложение точно приняло текст только по успешной записи fd |
| Контекст поля/окна | подтверждённый backend и актуальная generation | что неизвестный контекст безопасен для автокоррекции |

У обычного Wayland `wl_keyboard` события фокуса и клавиатуры относятся к поверхностям клиента; наличие этого объекта не даёт глобального наблюдения чужих приложений. Поэтому Wayland должен описываться по проверенной интеграции с конкретной средой, а XWayland — отдельной областью. Это ограничение следует из [Wayland protocol, wl_keyboard](https://wayland.freedesktop.org/docs/html/apa.html#protocol-spec-wl_keyboard), а не из качества Rust-обёртки.

### Сначала доказать прозрачный транспорт

Первые этапы разработки должны проходить с полностью отключёнными текстовыми преобразованиями. Для каждого supported native event необходимо сравнить входной trace и output trace; отдельно испытать повтор, модификаторы, две клавиатуры, held-key attach/detach, блокировку сессии, reconnect и fail-open. Подтверждать следует конечное состояние и семантику событий, а не только отсутствие ошибки `write`.

При включении grab необходимо определить, как устраняются уже удерживаемые клавиши. Просто начать перехват посередине нажатия недостаточно: desktop мог получить Down от физического устройства до grab, а Up придёт через другой источник. Нужен проверенный протокол активации на согласованном состоянии; допустимый первый вариант — ждать, пока все клавиши источника отпущены.

### Восстановление должно быть частью протокола

Нормальный выход, отказ инжектора, потеря reader, `SYN_DROPPED`, смерть worker, зависание, потеря сессии и hotplug — разные переходы. Для каждого задаются: владелец grab, владелец pressed-set, действие с виртуальными удержаниями, срок завершения и наблюдаемый статус. «Drop выполнится когда-нибудь» и лог ошибки не заменяют протокол.

Fail-open означает возврат пользователю рабочего физического ввода. Он не обещает откат уже частично отправленных символов и не гарантирует сохранение нажатия, пришедшего ровно в момент сбоя. Эти границы должны быть измерены и отражены в тестах. Обычные функции анализа/GUI не должны задерживать владельца grab.

### Не наращивать вторую реализацию reader параллельно первой

Оставшийся неиспользуемый `evdev_source.rs` содержит противоположный offset `+8` и `mem::forget(dev)` при grab (`строки 41–46,90`). Он не является рабочим fallback и не служит доказательством корректности активного backend. В будущем следует удалить либо явно изолировать устаревший вариант после создания контрактных тестов, чтобы исправления не попадали в мёртвый файл.
