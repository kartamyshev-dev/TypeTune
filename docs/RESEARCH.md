# Исследование Caramba Switcher Pro

## Границы доказательств

Исследуемый оригинал: 2026.10.07 (20261007.1), локальная копия установленного bundle.
Статические находки описывают поставленные байты и структуру данных, но не
доказывают выполнение функции. UI наблюдения показывают доступность элементов,
но не качество алгоритма. Live сравнение требуется отдельно.

Идентичность: universal executable SHA-256
`d2855030616863709a571a076777d1eea64adf4d4d3ee065555ca3513b5a63e5`;
выделенный arm64 SHA-256
`19d0057a9bfc38ba590babff82b28b5bf496c0833bbbd221f502722c6e2a26e9`.
Manifest всех файлов: `research/evidence/original-manifest.json`.
REA Mach-O Evidence: `ev_342e7b6c340402bded108d76b34eb55eda0e1c0fd06d45d33d754d0641724c7e`.

## Проверенные ресурсы и интерфейс

Parent-агент через CUA наблюдал главное окно, доступные tiles и исключения
слов/приложений; Pro trial отображался до 17.10.2026. Это наблюдение интерфейса,
не результат runtime приёмки алгоритма.

Поставленные строки UI описывают следующие функции: автопереключение,
исправление опечаток, ёфикатор, Single Shift, Double Shift/Option для слова
или выделения, одновременные левый и правый Shift для паузы, paste without
formatting, звуки, исключения, пользовательские правила, статистика времени.
Ссылки на Caramba Clear, Timer и Time and Day относятся к рекламе других
приложений: включение этих функций в Switcher не доказано.

В ресурсах есть отдельный framework UI и login helper. Подробнее см.
реестр `docs/FEATURES.md`.

## Хранилище исключений

Проверена только поставленная модель `Caramba.momd/Caramba.8.mom`;
личные строки базы данных не читались. REA Evidence:
`ev_8ed31ebf42477ac0055078501fb15f1f96ac3730a8b1466271ccc94b582e36b3`.
Компактное авторское представление: `research/evidence/coredata-schema-summary.json`.

- `AppException`: optional `enabled` Boolean, `bundleID` String, `path` String.
- `AutoswitchException`: optional `pattern` String, `additions` Int16 с default 0,
  `visible` Boolean с default false, `disabled` Boolean.
- В модели у pattern есть проверки `length > 1` и `length < 100`.

Наличие дополнительных Swift строк фильтрации позволяет предположить более
строгую проверку при добавлении правила. Точное сочетание проверок без
прослеживания кода и UI экспериментов пока неизвестно.

## Предварительная карта движка

Импорты Mach-O подтверждают обращения к CGEventTap, CGEventPost/CGEventPostToPid,
TIS источникам ввода и IsSecureEventInputEnabled. Наличие импорта не доказывает,
что конкретный сценарий проходит через этот API.

Точные байтовые смещения выбранных маркеров сохранены в
`research/evidence/engine-marker-locations.json`; это literal scan и Mach-O
segment mapping, не доказательство вызова.

В строках arm64 исполняемого файла обнаружены Rust source markers
`src/keyboard.rs`, `src/event_tap/layout_converter.rs`, `src/event_tap/layout.rs`,
`src/app.rs`; Swift содержит bridge и контроллеры UI. Это признаки вшитого Rust
движка, а не восстановленный исходный проект.

Строковые метаданные модели содержат Kbm и KbmFeature; среди имён полей есть
weight, is_known_word, is_case_sensitive, is_double_caps_preventative.
AutocorrectRule содержит prefix_len, suffix_len, insert_id, case_sensitive,
is_yofikator. Эти имена пока не дают точной математической модели решения.
Параметры special_behaviors упоминают switch_to_en_on_focus, задержки до
Backspace/retyping и повторы активации раскладки. Числовые значения и применимость
к приложениям пока не установлены.

Следовательно, использование системного spellchecker и самостоятельных
эвристик в прототипе нужно считать собственной реализацией. Эквивалентность
оригиналу устанавливается только независимым корпусом и live сравнением.

## Неизвестное и продолжение

- Точный порог классификатора, словари, приоритеты и границы слов.
- Полный путь события, замены, отмены и обучения.
- Ё и typo правила, кроме наличия соответствующих функций/полей.
- Работа во всех приложениях, точность и скорость.
- Эквивалентность прототипа оригиналу.

REA/Ghidra 12.1.4 выполнил первичный arm64 анализ: 24484 процедур и 40952
строк (полученные counts нужно сверять с `research/evidence/snapshot-replay.json`).
Overview Evidence: `ev_b7dc8cbeedb8ce20c80f84fcd1da98928aa180e25c8594bc6d3898a8ac17a046`.
Повторный CLI запрос с сохранённым snapshot вернул тот же Evidence ID;
результат: `research/evidence/snapshot-replay.json`. Это проверка повторного
чтения неизменяемых доказательств, а не сохранения живой базы Ghidra:
REA удаляет временный проект при закрытии.

Дальнейшие findings должны ссылаться на функции и адреса с тем же SHA-256,
а декомпиляцию сверять с инструкциями.

Входной tap создаётся на HID уровне (0), а найденная выдача собственных клавиш
идёт на session уровне (1). Это объясняет возможное отсутствие реакции на
инструмент, который вставляет текст через AX или постит ниже HID tap. Само по
себе это не доказывает способ ввода конкретного UI инструмента.

Проверен контракт REA `capture_native_ui_scenario`: key-entry устанавливает
AXValue (`bridge/native/ReaNativeUI.swift:107`), а не отправляет HID клавиши.
Он не является подходящим oracle для алгоритма переключения. Физический ввод
или отдельно проверенная выдача событий на HID уровне остаются необходимыми.

В выбранном входном пути не обнаружен фильтр sourcePID/userData: прямые
CGEventGetIntegerValueField callsites связаны с keycode field9. Это ограниченный
результат поиска, не доказательство отсутствия других фильтров во всём приложении.

### Ограничение псевдокода

Ghidra не восстановил корректные ABI/сигнатуры ряда системных thunk-вызовов:
псевдокод иногда показывает константу вместо возвращённого регистра x0.
Поэтому выводы о tap creation, AX/Secure Input gate и location выдачи сверены
с raw ARM64 instructions. Псевдокод Rust state machine содержит много
неопределённых типов и служит картой последующего анализа, а не исходником.

Глубокая сессия закрыта через close_binary; экспортировано 37 Evidence records
в private bundle и сохранён private snapshot. Число unknowns=0 в export metadata
означает отсутствие записанных REA unknown records, а не отсутствие неизвестных
алгоритмов. Неизвестные исследовательские вопросы перечислены выше.

## Продолжение: dispatch и преобразование

В сохранённом `FUN_100251f20` обнаружены раздельные отчётные флаги:
bit0 сообщает double-caps, bit16 сообщает autoswitch; bit32 сообщает ё,
а при его отсутствии bit24 сообщает typo. Это порядок генерации статистических
событий: он **не устанавливает** порядок применения правил matching.
Авторская привязка литералов: `research/evidence/dispatch-event-marker-map.json`.

В нескольких ветвях сравниваются исходная и целевая последовательности клавиш:
совпадающий префикс оставляется, а изменяющиеся хвосты передаются в
`FUN_10025a220`. Рядом есть literal сообщения об оптимизации повторного ввода.
Такой путь отличается от безусловного удаления и повторного набора всего слова.
Порог/применимость оптимизации по приложениям ещё не восстановлены.

На повторном проходе исследованы classifier `FUN_1002d9888`, feature gate
`FUN_100255420`, reducer `FUN_100255af0` и непосредственно retype
`FUN_10025a220`. Один новый persistent import использован для получения этих
недостающих функций; уже полученные evidence использовались из snapshot.

## Уточнённые алгоритмы: второй проход

Индекс Evidence второго прохода: `research/evidence/algorithm-finding-ledger.json`.
Функции ниже декомпилированы; для input state, feature gate, retype и scoring
дополнительно сохранены ARM64 инструкции. Имена FUN — адресные имена Ghidra.

### Буфер и повторная коррекция

- `FUN_1002519b0` сохраняет буфер на key-up, на key-down Tab (0x30) очищает его,
  Backspace (0x33) удаляет последнюю запись, другие key-down добавляют запись.
  Отдельные события reducer очищают буфер целиком либо заменяют его.
  Есть отдельная обработка дефиса при выделении хвоста.
- `FUN_1002e3c28` — точный byte predicate: последний UTF-8 byte принадлежит
  `TAB, LF, CR, SPACE, '-'`. Это часть логики границ, **не полная** сегментация слов.
- `FUN_100255420` проверяет три независимых automatic feature bytes. Если все
  отключены, анализ не выполняется. Прямое сопоставление каждого байта с UI
  preference не восстановлено; правило «один флаг отключает всё» не доказано.
- Тот же gate пропускает Backspace и сравнивает текущий текст с сохранённым
  состоянием прежней коррекции по взаимному префиксу. На несовпадении старое
  состояние освобождается. Это свидетельство защиты от повторных коррекций;
  пользовательское обучение и точная Undo semantics ещё требуют исследования.
- `FUN_10025575c` сбрасывает флаг прежней коррекции и освобождает optional
  сохранённый текст/раскладку.

### Последовательность преобразований и ё

`FUN_1002e10b4` выполняет отдельные стадии: double-caps → переключение языка →
опечатки/ё. Первая стадия проверяет, что первые два Unicode символа uppercase,
а третий lowercase. Автопереключение вызывает virtual method модели; typo/ё
передаются в `FUN_1002dbdfc` отдельными enable-аргументами. Это установленный
порядок верхнего уровня; полный порядок конкурирующих правил внутри модели
ещё не восстановлен.

Rule engine сначала получает кандидаты из графа. В `FUN_1002dbb34` при наличии
uppercase выполняется дополнительный поиск по приведённому регистру с
объединением/удалением совпадающих кандидатов. `FUN_1002dbdfc` имеет раздельные
фильтры typo/ё, ветвь определения вставки из одного символа U+0451 и сохраняет
признак ё в отчёте применённого правила. Конкретные правила, словари и вставки
из оригинала в прототип не переносились. Поведение case-sensitive rules и
пересекающихся кандидатов пока описано лишь частично.

### Весовой выбор языка

Прослежена цепочка runtime model vtable → `0x1002e6424`/`FUN_1002df804` →
`FUN_1002e083c` → `FUN_1002e0cec`. Верхний wrapper явно рассматривает RU/EN.

По ARM64 инструкциям `FUN_1002e0cec` складывает ненулевые 32-bit веса
подходящих записей (record+0x24) и возвращает сумму в x1 вместе с категорией
в x0. Записи с нулевым весом обрабатываются отдельными boolean категориями.
`FUN_1002e083c` для обычной весовой категории выбирает больший signed вес;
при равенстве сохраняет ранее выбранного кандидата. Другие категории имеют
отдельные ветви, поэтому этот алгоритм нельзя свести к единственному
«confidence > threshold».

Фиксированный универсальный порог не найден в исследованном фрагменте.
Численные веса, набор признаков, правила категорий и полный алгоритм
применения модели не восстановлены. Системный NSSpellChecker не является
эквивалентом этой модели без независимого измерения.

Evidence evaluator pseudocode:
`ev_255b39337cc3ba5b02da7915aed65ce67ee7abab2e41f557cc20d26056f3327c`;
все связанные ASM Evidence и параметры адресов — в algorithm finding ledger.

### Выдача исправления и задержки

`FUN_10025a220` сначала пытается активировать целевой input source, проверяет
текущий источник, затем отправляет удаление и набор изменённого хвоста.
Число повторов активации ограничено сверху 10; retry sleep ограничен 500 мс;
задержка возле удаления также ограничена 500 мс. Отдельный аргумент вызывает
Space перед удалением; другой выбирает flags=0x40000 для Backspace вместо 0.
Применимость этих аргументов к конкретным приложениям не установлена.

Если попытки активации исчерпаны, функция переходит к выдаче клавиш; отдельного
доказанного fail-closed abort на этой ветви нет. Это поведение оригинала не
является требованием повторять рискованную замену в самостоятельном прототипе.

Численные значения из модели не прочитаны; caps — пределы в исполняемом коде,
а не измеренные рабочие задержки. Evidence ASM:
`ev_f9fed34782aa76925320b9c9897dff0e467a386f0d538a4ccb17d8e8ea7abf86`.

Второй проход завершён; сессия закрыта. Private bundle содержит 69 Evidence
records; все 32 записи algorithm finding ledger присутствуют в экспорте.
Readback: `research/evidence/algorithm-export-verification.json`.
Точный дальнейший static checkpoint: разбор категорий evaluator

## Проверка сохранения именно Ghidra project

Критерий сохранения `.gpr` и повторного открытия через REA остаётся
**не выполнен**: установленный REA 6.5.0 Ghidra provider этот lifecycle не
поддерживает. Проверены его installed implementation и фактические schemas
open/close; в `research/private` нет `.gpr`, `.rep` или `.gzf`.

`GhidraLauncher` запускает headless import с `-readOnly -deleteProject`.
В контракте `close_binary` доступны только `snapshot_path` и `overwrite`;
параметр snapshot сохраняет Evidence JSON и не сохраняет Ghidra project.
Provider capabilities прямо указывают, что временная база удаляется при
закрытии и сохранённые аннотации не являются сохранённым Ghidra project.

Авторское доказательство с SHA-256 implementation файлов и строками anchors:
`research/evidence/ghidra-project-lifecycle.json`. Повторный import ради этой
проверки не запускался: он снова создал бы удаляемый проект и не доказал
save/reopen. Уже проверенный snapshot replay считается отдельным результатом.
Для закрытия `.gpr` критерия понадобится другой поддерживающий persistent
project путь или отдельный Ghidra workflow; выполнение такого пути через REA
в текущей версии не подтверждено.

Уточнение категорий evaluator по ранее сохранённым инструкциям:
[RESEARCH_FOLLOWUP](RESEARCH_FOLLOWUP.md). Извлечение признаков и смысл
категорий по-прежнему не восстановлены; новые запросы не выполнялись.
