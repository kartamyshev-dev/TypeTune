# F05: ручное преобразование выделенного текста Caramba

Текущий результат: callee selection раскрыт в существующей Ghidra базе;
CmdC → чтение/конверсия → CmdV → восстановление только string доказаны статически.
Native synthetic LF/TAB/emoji/NFD подтвердил конверсию и каретку в конце.
Начальные cache-only ограничения ниже оставлены как история исследования;
они уточнены разделом «Узкий Ghidra follow-up». Полное F05 остаётся открытым.

Target — frozen arm64 main Caramba2026.10.07, SHA-256
`19d0057a9bfc38ba590babff82b28b5bf496c0833bbbd221f502722c6e2a26e9`.
Этот проход читает только существующие private REA exports и поставленные
ресурсы. Новых imports/сессий, UI/HID/runtime-проверок и изменений прототипа нет.
Индекс: `research/evidence/selection-research-findings.json`.

## Подтверждённая граница функции

Локализованные RU/EN строки обещают Double Shift или Option для набранного
слова **или выделения**. Реализация выделения не выводится только из этой строки:
в сохранённом псевдокоде dispatch `0x100251f20` найден отдельный callsite.

Ручная ветвь после разрешения gesture получает доступные раскладки, целевую
раскладку и текст локального key buffer. В блоке после label `0x100253820`
проверяется `local_a0 == 0` либо результат predicate `0x1002e3b90`:

- При пустом локальном тексте либо положительном predicate вызываются
  event/statistics helper `0x100259288` с адресом `0x10042841d`, длиной24
  (точные frozen bytes — имя события `caramba_selection_switch`), затем
  **`0x10025935c` с парой аргументов доступных источников ввода**.
- Иначе вызывается event marker `0x10042840a`, длиной19 —
  `caramba_doubleshift`, после чего продолжается известный word retype путь
  с буфером клавиш и `0x10025a220`.

Это доказанная статическая развилка между word-ветвью и отдельной
selection-ветвью. Назначение `0x10025935c` как selection converter — вывод
из *ветви и маркированного callsite вместе с UI-контрактом*. Как эта функция
получает текст выделения и производит замену, пока неизвестно.
`0x1002e3b90` не раскрыт в изученном cache; называть его whitespace-проверкой,
проверкой реального выделения или multiline predicate нельзя.

Источник полной dispatch-декомпиляции:
`ev_22551d5be75cb66f6fa304046951cfbd21865eedd28e2f1850f0ad3064b9e18f`;
страница с нужной ветвью:
`ev_354d6350f581bcd01bb375fc8b01f8c2b15f362bda04801325894ae57a07599a`.
Это псевдокод с незавершённым распространением типов; точные аргументы и
сигнатуры require ARM64 corroboration перед переносом алгоритма.

## Trigger: что уже видно, что ещё требует инструкций

Сохранённый reducer `0x1002516ec` сравнивает временные отметки и идентичность
кнопки, выдаёт варианты0..4. В dispatch ручная ветвь допускается при
состоянии4, если не активен отдельный опциональный флаг app+0x157.
С опциональным флагом используется время прошлого modifiers-события и
app+0x10/+0x18 (порог точно не восстановлен).

Для keycode0x3a/0x3d (левый/правый Option) дополнительная проверка разрешает
переход на release: в предыдущих aggregate flags присутствует только Option,
в текущих не разрешены конфликтующие модификаторы, и Option уже отпущен.
Иначе ветвь не выполняется. Это наблюдение псевдокода, а не выполненный жест.
Связь app+0x157 с конкретной настройкой и точные временные границы должны
проверяться по setter-коду/ARM64, а не по похожим числам в ABI-неточном выводе.

Reducer Evidence:
`ev_69c60ebb97abfe5a0c3c2bdb9fd16c9e31432ef12bf53b7984cf7021ba00845f`.
Отдельный SplitshiftController `0x1000075cc` относится к двум Shift/паузе;
он не заменяет доказательства Double Shift selection path.

## Clipboard и multiline: пока открыты

В cached bundle из138 records (hotkey export) нет тела `0x10025935c`.
Также нет тела string utility `0x10024b614`, вызываемой другими gates.
Поэтому **Cmd+C, чтение NSPasteboard, transform по строкам, Cmd+V и восстановление
clipboard для selection не установлены**. Это не отрицание их существования.

`0x100022cb4` действительно читает generalPasteboard, временно оставляет
plain string и вызывает keyboard emitter с последующим отложенным restore.
Но это уже установленный plainPaste путь. Нет доказанного перехода
`Double Shift/Option → 0x10025935c → 0x100022cb4`; переносить его устройство
на selection по аналогии нельзя.

Rust binary содержит строковые маркеры objc2-app-kit NSPasteboard и
`generalPasteboard`, то есть clipboard доступен в его коде; literal marker
не устанавливает конкретного caller или алгоритм. Повторный общий AX scan
не проводился. Полнота работы многострочного выделения, переносов LF/CRLF,
TAB, emoji и clipboard restoration требует раскрытия callee и native опыта
на отдельном синтетическом документе.

## Следующий один узкий пакет

После закрытия текущей сессии другим исследователем достаточно получить
**из существующего Ghidra project**, без нового import:

1. Псевдокод и инструкции `0x10025935c`: исходный selection path, его callees.
2. Псевдокод и инструкции `0x1002e3b90`: смысл ветви отказа от word buffer.
3. Инструкции reducer `0x1002516ec` и только relevant dispatch block
   `0x1002536xx–0x1002539xx`: trigger, точные аргументы и сигнатура selection.
4. `0x10024b614` — только если потребуется для единицы длины, это вторичный
   вопрос и его нельзя путать с чтением editor selection.

После callee-map расширять только недостающие clipboard/readback/restore узлы.
Текущий REA/Ghidra процесс занят другим исследователем: этот пакет
**не запускался**. Full F05/reverse-engineering acceptance остаётся открытой.

## Узкий Ghidra follow-up: copy/paste и точные пороги жеста

После освобождения исследовательской сессии получен один пакет из существующего
persistent project: `-process caramba-arm64 -noanalysis -readOnly`, exit0,
marker `SELECTION_PROBE_SAVED`. Исходный SHA программы проверен самим script.
Запрошены только два новых псевдокода — `0x10025935c` и `0x10024b614`; к ним
инструкции, инструкции gesture reducer и bounded dispatch0x100253600–0x1002539ff.
Это Ghidra-complement к REA, **не новый REA Evidence record**. Отчёт/скрипт/логи
остались private; digests включены в авторский индекс.

### Развилка selection установлена инструкциями

`0x100253894–0x1002538a4` проверяют непустую длину и вызывают predicate
`0x1002e3b90`; при пустом буфере либо true переходят в selection-ветвь.
`0x1002538a8–0x1002538bc` посылают selection marker;
`0x1002538c0–0x1002538c8` передают x24/x25 и вызывают `0x10025935c`.
Это прямой callsite, а не связь по одному имени строки.

### Selection: что уже подтверждено непосредственно

`0x10025935c` сначала получает строкоподобный snapshot через `0x1002598ac`,
затем вызывает writer `0x100259998(1,0)` с пустой последовательностью.
Далее ARM64 `0x1002593a8–0x1002593b0` выдаёт **Cmd+C**:
keycode0x08, flags0x100000 через уже доказанный keyboard-pair/session emitter.
Функция ждёт ровно200мс и снова вызывает `0x1002598ac`.

Результат проверяется через `0x10024b614`: новый helper разобран и сверён
с инструкциями. Он декодирует UTF-8 вперёд и назад и возвращает **подсрез ptr/len
после удаления Unicode whitespace по краям**, включая TAB/LF/CR/SPACE.
Это не длина в символах и не чтение editor selection. Если trimmed length0,
selection converter пропускает transform/paste и переходит к восстановлению
сохранённой строки. Исходный нетриммированный текст остаётся входом
преобразующего итератора; trim используется здесь как empty/whitespace gate.

Непустой результат разбирается iterator `0x10025c2e8`, части передаются в
`0x10025043c`, а результаты объединяются в строку. По телу iterator/transformer,
которых нет в текущем пакете, точная сегментация/правила LF и сохранение
whitespace ещё не доказаны. По накопленным весам источников выбирается
TIS source и активируется перед вставкой; полная семантика веса неизвестна.

В `0x10025968c–0x100259694` результирующая строка передаётся writer;
`0x1002596a8–0x1002596b0` выдаёт **Cmd+V**:
keycode0x09, flags0x100000. После второй200мс паузы
`0x1002596e0–0x1002596e8` writer получает ранее сохранённую строку.
Это доказанный copy/transform/paste/save-restore **dataflow**. Значение helpers
`0x1002598ac` и `0x100259998` как NSPasteboard read/write пока является сильным
выводом по Cmd+C/V и строковым аргументам; точные clipboard types, handling
errors и защита от перезаписи более нового clipboard требуют этих двух тел.
Они не были дополнительно запрошены сверх установленного лимита двух pseudo.

### Double Shift: строгие пороги в reducer

Сопоставление press/release с tag0/tag1 взято из ранее сохранённого dispatch
(проверяет aggregate+device-side Shift bits); сами пороги сверены по новым ASM.
Одна сторона Shift должна сохраняться во всех шагах:

| Переход | Условие | Инструкции |
|---|---|---|
| idle0 → firstPress1 | первый press после интервала **>100мс** от idle timestamp | 0x10025183c–0x1002518a8 |
| firstPress1 → firstRelease2 | release той же стороны, интервал **<300мс** | 0x100251910–0x100251988 |
| firstRelease2 → secondPress3 | press той же стороны, интервал **<300мс** | 0x1002517b0–0x10025182c |
| secondPress3 → secondRelease4 | release той же стороны, интервал **<750мс** | 0x100251724–0x1002517a0 |

Длительности вычисляются из seconds/nanoseconds в целые миллисекунды. Равенство
100 не проходит idle-условие; равенство300/750 не проходит последующие строгие
верхние границы. Другие event variants/конфликтующие modifiers могут сбрасывать
state; таблица не обещает полный gesture контракт без окружающего dispatch.

Возможная причина неудачного synthetic Double Shift после Cmd+A: если первый
press идёт не позднее100мс после сброса gesture state последним модификатором,
он не переводит state0 в firstPress1. Это **гипотеза по коду**, не установленная
причина фактического native опыта. Полезный разделяющий опыт: после полного
отпускания Cmd+A выдержать≥150мс, затем два Shift down/up с hold50мс и gap150мс,
ожидать≥500мс после второго release. Задержку самого helper/AX нужно включать
в фактические интервалы; один лишь параметр sleep не доказывает попадание
в предел300мс. Если каждый press/release занимает более300мс, жест не завершится.

Remaining gaps: pasteboard read/write/error/change-count guard; predicate2e3b90;
iterator25c2e8/transform25043c; exact Option enable/duration gate. Полноценная
native приёмка single-line/multiline selection остаётся открытой.

## Clipboard helpers: отдельный второй узкий пакет

Получены только тела и ARM64 `0x1002598ac`/`0x100259998` из той же базы,
без import/auto-analysis. Exit0 и `CLIPBOARD_PROBE_SAVED`; script требует тот же
SHA цели. Это второй Ghidra-complement, не REA Evidence record. Его SHA и
бюджет2 новых pseudo сохранены в author-written JSON.

**Тип установлен непосредственно:** оба helpers используют внешнюю константу
`NSPasteboardTypeString` через global import pointer `0x10055d3c0`.
На уровне AppKit это `.string`; речь о текстовом представлении, а не snapshot
всех item/type/data. Код преобразует Rust UTF-8 string в NSString перед записью.
Нельзя путать кодировку Rust-буфера с полным набором UTI-представлений pasteboard:
сам writer передаёт один `NSPasteboardTypeString`, а не самостоятельно объявленный
список `.string` плюс дополнительные UTF-8/UTF-16 типы.

`0x1002598ac`:

- Через `0x100260258` получает объект, через `0x1002601f0` читает по
  NSPasteboardTypeString. Сочетание с парным writer и Cmd+C/V dataflow
  подтверждает clipboard read; точные ObjC selector wrappers не декомпилировались.
- Nil → пустая Rust String `(capacity0,ptr1,len0)` в
  `0x100259944–0x10025994c`. Это не optional, различающий «clipboard пуст»
  и «текстового типа нет».
- Непустой NSString форматируется в собственный Rust UTF-8 буфер через helper;
  ошибка форматирования вызывает panic `0x100259914→0x10025996c`.
- Другие clipboard types/items нигде в этом теле не сохраняются.

`0x100259998`:

- Формирует NSArray ровно из одного NSPasteboardTypeString, count1
  (`0x1002599c4–0x100259a0c`).
- `0x100259a18–0x100259a24`: передаёт объект, type-array, owner0 в
  `0x100260370`. Это объявление набора типов по dataflow/контракту аргументов;
  exact selector/clear semantics нижнего wrapper в этом лимите не разобраны.
- `0x100259a28–0x100259a30`: ptr/len Rust UTF-8 → NSString.
- `0x100259a38–0x100259a44`: запись строки с NSPasteboardTypeString через
  `0x100260304`. Результат сразу сменяется освобождением NSString: проверки
  success/Bool и обработки recoverable write failure в этом caller нет.
- Nil при создании NSArray приводит к no-return panic
  `0x100259a14→0x100259ab8`; ObjC messaging failures в нижних wrappers не исследованы.
- В этом теле нет вызова changeCount, сравнения сохранённого snapshot,
  повторного чтения перед restore или сохранения других типов.

По совокупности selection converter **восстанавливает только старую строку**.
Если старое содержимое clipboard было rich text/несколько items, восстановление
ALL representations в этом пути не доказано и противоречит ограниченности
snapshot только .string. Если clipboard изменён другим источником за время
200мс после paste, этот caller не защищает новый clipboard от перезаписи.
Риск — наблюдённая статическая особенность, а не проведённый опыт с данными.

Для защищённого reference-native опыта следует хранить пользовательские
ALL types/items только в RAM, работать с собственным nonce и возвращать их
лишь после доказанного exact readback собственного состояния. Факт записи
оригиналом .string не разрешает принимать произвольный clipboard по одному
совпадающему text value. AppKit может предоставлять дополнительные представления;
реальный набор следует сверять полностью на собственном nonce, без перезаписи
неизвестного/более нового содержимого. Здесь UI/native проверки не выполнялись.
