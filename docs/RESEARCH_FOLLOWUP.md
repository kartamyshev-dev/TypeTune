# Статическое уточнение категорий классификатора

Изучен уже сохранённый private Evidence bundle (69 записей), без нового
Ghidra import, UI, событий клавиатуры и изменений Sources/Tools.
Все адреса относятся к arm64 SHA-256
`19d0057a9bfc38ba590babff82b28b5bf496c0833bbbd221f502722c6e2a26e9`.
Компактные claims/anchors и digest bundle: `research/evidence/static-followup.json`.

## Категория и вес — разные результаты

ARM64 `FUN_1002e0cec` возвращает категорию в w0, сумму в x1. Для совпавшей
языковой пары ненулевой 32-bit вес записи прибавляется к сумме. У записей с
весом 0 рассматривается младший бит поля record+0x18; два накопленных флага
потом определяют категорию:

| Состояние обработанных записей с нулевым весом | Категория w0 |
|---|---:|
| Таких записей нет | 1 |
| Есть только записи с младшим битом 1 | 2 |
| Есть хотя бы одна запись с младшим битом 0 | 3 |

Следовательно, смешение битов 0 и 1 даёт категорию 3. Вес и его знак сами по
себе не меняют категорию 1 на 2 или 3. Семантическое имя поля record+0x18
не восстановлено; называть его подтверждённым `is_known_word` пока нельзя.

Отсутствие совпадающей языковой пары даёт категорию 0. Это отличается от
совпавшей пары с пустым набором признаков: последняя даёт категорию 1 и вес 0.
На пути категории 0 регистр x1 не инициализируется как сумма, и вызывающий
агрегатор его не использует. Его нельзя показывать как достоверный вес.

Опорные инструкции: 0x1002e0e60–0x1002e0e88, 0x1002e0ed0–0x1002e0edc,
0x1002e0f40–0x1002e0f58; Evidence
`ev_dc4ca2427cec9987472c0444b6f5ed0b41d0da44de0005bd1275c566c8e189fe`.

## Приоритет в агрегаторе двух кандидатов

`FUN_1002e083c` применяет следующие ветви:

- Категория 0 пропускается.
- Категория 1 участвует в сравнении signed 32-bit сумм. Большая сумма побеждает;
  при равенстве сохраняется ранее выбранный кандидат.
- Категория 2 сохраняется отдельно и при отсутствии категории 3 получает
  преимущество над победителем по весу. Повторная категория 2 заменяет
  предыдущего кандидата этой категории.
- Категория 3 ставит сохраняющийся до конца флаг, который формирует результат
  `0x8000000000000002`, даже если уже был кандидат категории 2 или 1.

Это точнее общей формулировки «выбирает максимальный вес»: сравнение весов
действует только внутри категории 1. Названия и продуктовые причины категорий
не установлены. Численного универсального порога уверенности этот фрагмент
не подтверждает.

Anchors: 0x1002e0910–0x1002e0994, 0x1002e09b4–0x1002e09b8,
0x1002e0b94–0x1002e0c08; Evidence
`ev_93408285a7e01902352121bc95fd3fe4ba0f6db4cfc36ec13c6afdab171bdfc7`.

## Досрочное окончание извлечённых признаков

В evaluator первый word записи со значением -2 переводит выполнение из
цикла накопления в очистку оставшихся записей. Уже накопленные сумма и
категорийные флаги сохраняются. Условия, при которых extractor выдаёт этот
sentinel, неизвестны. Его нельзя считать подтверждённым исключением слова,
ошибкой или пользовательским обучением.

Anchors 0x1002e0e54–0x1002e0e5c и 0x1002e0ee0; тот же evaluator ASM Evidence.

## Исторический остаток до следующего прохода

В сохранённом bundle нет тела `FUN_1002e0030`: есть только вызовы этой функции.
Поэтому точные признаки, их сопоставление, источник record+0x18 и смысл
sentinel -2 не восстановлены. Требуются следующие недостающие REA запросы
в будущей разрешённой сессии:

```json
{"name":"procedure_pseudo_code","arguments":{"procedure":"0x1002e0030"}}
{"name":"read_function_instructions","arguments":{"procedure":"0x1002e0030"}}
```

Они сейчас не выполнялись. Сохранённых сведений также недостаточно для новых
утверждений об Undo/learning; поведение прототипа и результаты текущего
native-прогона этим статическим уточнением не изменяются.

## Дополнение 2026-10-15: тело extractor получено

Выполнены оба ранее недостающих запроса к0x1002e0030. Перед запуском проверен
сохранённый deep-snapshot с тем же хешем arm64 и профилем; повторный импорт
понадобился только для отсутствующих запросов. Получены515 инструкций,
непрерывное тело0x1002e0030–0x1002e083b (2060байт), псевдокод. Сессия закрыта,
новые Evidence/snapshot сохранены только в private. Компактные claims, anchors,
IDs и хеши: research/evidence/extractor-followup.json.

Наблюдения ASM + псевдокода:

- Результат вспомогательной функции0x1002e1d98 возвращается раньше fallback,
  если его длина ненулевая. Называть это полным словарным поиском пока нельзя:
  тело helper отдельно не прослежено.
- Fallback обходит UTF8 с концов. Два набора отбрасываемых суффиксных символов:
  `! ( ) + = _` и `! $ & ( ) * + - / ? @ ^`. Выбор зависит от младшего байта
  шестого аргумента и последнего байта из набора TAB/LF/CR/пробел/дефис.
  В обоих вариантах также обрабатываются ведущие дефис и открывающая скобка.
  Это наборы в конкретных ветвях, не спецификация всей пунктуации приложения.
- Затем вызываются форматирование/вспомогательный TLS-поиск и iterator.
  Выходные записи копируются шагом40байт. Значение первого слова -2 у iterator
  заканчивает копирование; оно не копируется как обычный элемент. Следовательно,
  прежнюю ветвь evaluator по sentinel нельзя без дополнительных сведений
  интерпретировать как пользовательское исключение или обученное решение.

Псевдокод предупреждает о неустойчивом распространении типов и удалённых
недостижимых блоках; Ghidra также считает один вызов no-return. Имена семантических
полей, точный смысл режима, нормализация, источники весов и структура справочников
остаются неизвестными. Эти наблюдения не переносились в код либо словари
LayoutPilot и не меняют выводы native-сравнения. Следующие точечные запросы:
0x1002e28c4,0x1002e1d98,0x1002e477c,0x1002e6124 и данные форматных строк
0x1004dac93/0x1004dac99. Повторное чтение из snapshot предпочтительнее импорта.
