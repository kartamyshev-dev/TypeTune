# CODEX-001 — выделение и удаление слова в Codex

## Наблюдение пользователя

После слова и Space в поле текущего разговора Codex слово выделилось и исчезло.
Слово/раскладка не сохранены. Пользователь предполагает повторение для всех слов;
это не проверенный универсальный результат. Последний запущенный кандидат —
b911718f, но digest процесса непосредственно при инциденте не снят.

## Что установлено по коду

AccessibilityEditor раньше допускал любой host с writable AXSelectedText.
Он выделял диапазон, устанавливал выбранный текст и проверял итог; при неудаче
возвращал uncertain. Такой readback не отменяет уже произошедшую потерю текста.
Идентичность поля и writable-ответ сами по себе не доказывают корректный контракт
веб-редактора. Точный механизм удаления в Codex пока не воспроизведён.
Автоматический откат через ещё одну неподтверждённую запись не добавлен: при
асинхронной вставке он мог бы повторно изменить новый пользовательский текст.

## Защитное изменение

EditorSupport разрешает только TextEdit. Policy вызывается перед обработкой
клавиш, до AX-снимка и первым условием рабочего replace. При неизвестном host
нет AX-чтения поля/выделения/записи и подавления обычных команд коррекции.
В TextEdit требуются TextArea, окно и совпадение AXSelectedText с ожидаемым
фрагментом после выбора диапазона; при несовпадении запись не выполняется.
Это ограничение совместимости, не восстановление работы коррекции в Codex.
В UI явно указан TextEdit. Общая задача аналога для других приложений открыта.

- CLI212/212 в debug и release; корпус4420/4420, без изменения правил языка.
- EditorGuardProbe компилируется с рабочим AccessibilityEditor.swift и настоящим
  LayoutPilotCore. Для5 неподдержанных hosts replace останавливается до sentinel

Evidence: research/evidence/codex-loss-containment.json и codex-loss-guard-*.

## Исправление Chromium, 2026-10-15

Пользователь разрешил отдельную локальную страницу Chrome LP-CODEX-001.
На contenteditable воспроизведён механизм: AXSelectedText вернул success,
но не изменил `ghbdtn ` и оставил выделенным слово. Следующий Space заменил
выделение: остались два пробела. Это прямой опыт Chrome, а механизм конкретного
инцидента в поле разговора Codex остаётся выводом по сходству Chromium.
Переписка не использовалась как тестовое поле.

Для Chrome/Codex добавлена самостоятельная выдача одной пары Unicode CGEvent
в проверенный PID вместо AXSelectedText. Нет отдельного удаления/clipboard.
Асинхронное изменение текста и курсора подтверждается readback до завершения
операции. При no-op снимается только собственное неизменившееся выделение;
чужой текст не откатывается. TextEdit сохраняет отдельную AX-ветвь.

Проверка реального AccessibilityEditor из исходников: `ghbdtn ` → `привет `,
курсор UTF16=7, выделение0, result=verified. При инъекции no-op текст и курсор
восстановлены; следующий Space оставил `ghbdtn  `. Evidence:
`chromium-selection-ack-production.json`, `chromium-noop-restored-selection.json`,
`chromium-noop-next-space.json`. Отдельные первые неудачные попытки сохранены.

REA проследил оригинальный путь физических Backspace/retype, session events,
private CGEventSource: [CARAMBA_REPLACEMENT](CARAMBA_REPLACEMENT.md).
Новый адаптер — самостоятельная замена, не копия этого алгоритма.
GUI app e1c52501: после Touch ID существующая запись AX обновлена через UI.
Глобальный HID Space с настоящим LayoutPilot проверен6/6: оба поля Chrome,
коррекция/правильное слово/второй Space и20 слов потоком. В прогонах нет потери
или дублирования; точный UTF16 cursor и selection0 проверены readback.
Evidence chromium-gui-verification.json. LayoutPilot оставлен включённым.
Это ограниченная Chrome-проверка, не native-приёмка реального composer Codex.
