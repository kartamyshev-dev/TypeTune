## Что воспроизведено и исправлено

1. Снимок редактора принимал только `AXTextArea`. В однострочном поле страницы
   Chrome не работали ни автоисправление, ни Double Shift. Добавлен `AXTextField`
   только для Chrome и только с предком `AXWebArea` (поиск ограничен 16 уровнями).
   Поля паролей исключаются по subrole; адресная строка и панели браузера не
   допускаются. Прежние проверки PID, окна, текста, каретки и Secure Input сохранены.
2. После ad-hoc пересборки Универсальный доступ и Мониторинг ввода требуют
   отдельного обновления записи приложения. На промежуточной сборке после
   обновления только AX Double Shift работал, обычные клавиши не доходили до
   обработчика. Обновление существующей записи Мониторинга ввода и перезапуск
   восстановили auto на том же бинарнике. Теперь приложение отдельно проверяет
   `CGPreflightListenEventAccess`, при отказе приостанавливается и показывает
   «Нужен Мониторинг ввода», а не «Работает».

Какой браузер и поле использовал пользователь первоначально, неизвестно.
Это два наблюдённых локальных сбоя, а не доказательство причины каждого прежнего
неудачного запуска. Никакие словари, настройки original или модели не менялись.

## Запуск и продолжение

Пользователь может продолжать работать с уже запущенным `dist/LayoutPilot.app`.
Сначала ABC, затем `ghbdtn` и пробел в поле страницы Chrome или новом TextEdit.
Double Shift преобразует слово/выделение. Адресная строка, пароль и другие
браузеры в эту поддержку не входят.

После следующей пересборки завершить LayoutPilot; обновить **только его** запись
в обоих разделах «Управление устройством и доступ к данным»/Универсальный доступ
и «Мониторинг ввода», затем перезапустить. Не сбрасывать TCC целиком и не
выдавать доступ терминалу ради теста. При пересборке helper обновляется только
его отдельная запись. Перед каждым событием остаются проверки точного поля,
URL/документа, PID, AX/post permissions и Secure Input.

Следующая задача: пропуски быстрого потока и нестабильный Chrome rich F07 из
PLAN; новая длительная проверка окончательной сборки. Старые 32мин48сек и архивы
относятся к прежним SHA. Codex composer проверяет пользователь; Safari не
проверялся. Полная готовность по PLAN и функциональное равенство не заявляются.

## Chrome и ChatGPT: ранний режим — 2026-10-17

На установленном GUIefd117a0 сбой Chrome воспроизведён в собственной локальной
textarea: helper type-wrong при earlyCorrection=ON дал `приdtn  ` вместо `привет  `.
После выключения только раннего режима через UI тот же сценарий дал `привет  `;
выделенное слово + Double Shift + два пробела также оставило `привет  `.
[Сравнение](../research/evidence/diagnosis-2026-10-17/chromium-early-comparison.json),
[новая runtime-fixture](../Tools/fixtures/chromium/early-regression.json).
Это AX-наблюдения результата, не проверенный exit дочернего helper/strict suite.

Непосредственная причина воспроизведённого дефекта — экспериментальная замена
незавершённого слова в Chromium; точная ветка гонки suffix/replay/source ещё не
трассировалась. Ранний режим оставлен OFF, обычное automatic ON. Код, подпись,
разрешения, словарь и пользовательские исключения не менялись; пересборки нет.
Это обход дефекта конфигурацией, не исправление самого экспериментального режима.
До отдельного исправления/проверки не включать ранний режим для обычной работы.

Установленное `/Applications/ChatGPT.app` имеет bundle ID `com.openai.codex`,
который уже разрешён и использует keyboardEvents backend, как Chrome.
Отсутствие allowlist для ChatGPT не подтвердилось. По указанию пользователя
composer проверяет он сам; native ввод агента туда не выполнялся.
Запрошен физический повтор в привычных Chrome/ChatGPT полях, ответ ожидается.
Постоянный общий отказ исключён только в проверенном TextEdit-сценарии;
остальные пропуски быстрого потока и F07 остаются открытыми.
