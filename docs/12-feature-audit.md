# Аудит функций, управления и поставки

Дата: 2026-09-10. Baseline исходников: `8cc19d0`. Статус: исследование; описанные ниже исправления в runtime не внесены.

Этот документ фиксирует фактическое состояние corrector, snippets, config, CLI/IPC, GUI/tray и packaging/CI. Целевая реализация описана в [архитектуре](13-target-architecture.md), порядок разработки — в [плане](14-development-plan.md). Аудит устройств и Linux transport рассматривается отдельно; здесь он упоминается только там, где определяет достижимость функций.

## 1. Основания и границы проверки

- Прочитаны все исходники перечисленных компонентов, действующие manifests, Makefile, CI, packaging и прежние документы `04`, `06`–`10`.
- Координатор запустил `cargo test --locked -p typetune-core -p typetune-chatter -p typetune-config -p typetune-corrector -p typetune-snippets`: команда прошла, но каждый crate содержит **0 unit tests и 0 doctests**. Такой результат подтверждает сборку этих crates, а не поведение функций.
- Дополнительно выполнен изолированный Rust harness вне репозитория, с `path`-зависимостями на неизменённые `core`, `corrector`, `snippets`. Восемь утверждений о фактических выходных событиях прошли. Harness не открывал устройства и не запускал команды из сниппетов; результаты приведены в разделе 4.
- Выполнены проверки состава словарей и вычислений календарной формулы. Файлы словарей содержат по 10 000 уникальных строк, но это не подтверждает качество слов.
- Linux daemon, grabbing, D-Bus, GTK, systemd, установка и deb-сборка в этом аудите не запускались. Выводы о них основаны на коде и должны быть проверены на целевых стендах.

Метки доказательств: **S** — статически установленная ветка кода; **R** — дополнительно воспроизведена через публичный Rust API; **V** — требуется проверка на целевой ОС. Номера строк относятся к baseline `8cc19d0`; при изменении исходников их нужно перепроверять.

## 2. Что существует, а что только заявлено

| Возможность | Фактическое состояние baseline | Следствие для обещаний продукта |
|---|---|---|
| Автокоррекция RU/EN | Алгоритм и карты есть, входной `character` не заполняется | Не считать работающей функцией |
| Double-Shift | Есть обработка двух `Pressed`, но нет истории последнего завершённого слова и контракта жеста | Не обещать исправление «последнего слова» |
| Словари по 10K | По 10 000 строк, нет `hello` и `привет`, есть явно некорректные формы | Размер файла не является качеством словаря |
| Сниппеты | Есть suffix matcher и renderer, но matcher не получает символы; генератор теряет Unicode/Shift | Не считать раскрытие сниппетов работающим |
| Дата/время/shell | Есть код, календарь неверен, время UTC, shell синхронный | Сначала нужны отдельные контракты renderer и worker |
| Исключения приложений | Поля конфигурации существуют, потребителя нет | Терминалы, редакторы и приватные поля не защищены этими полями |
| Выбор раскладок | Поле `layouts` существует, код использует жёсткий `us,ru` | Конфиг не управляет фактической раскладкой |
| Typography | Только конфигурационные поля | Планируемая функция, не реализована |
| Hot reload | Меняет сохранённый `Config`, не действующий pipeline | GUI/IPC может сообщать новые настройки при старом поведении |
| D-Bus | Четыре метода есть, состояние основано на config; нет `ConfigChanged` из прежнего плана | Нужен контракт effective state и результата команды |
| GTK settings | Показ конфигурации и сохранение четырёх флагов | Не полноценный редактор настроек; применение не работает |
| Tray | Toggle, reload, exit; нет пункта Settings | Заявленный путь открытия настроек отсутствует |
| CLI start/stop/status | Реализованы через PID-файлы, но пути и lifecycle расходятся | Успех команды не равен готовности сервиса |
| deb/systemd | Есть исходные файлы и cargo-deb metadata | Установленный артефакт и его lifecycle не проверены |
| CI | Check, Clippy, Fmt на Ubuntu | Нет автоматической проверки поведения и пакета |
| Windows/macOS | Нет соответствующих backend implementations | Наличие переносимых Rust crates не означает поддержки ОС |

## 3. Текущие достижимые проблемы

### F01 — Текстовые функции не получают текст (P1; S, R)

`crates/typetune-input/src/lib.rs:219` создаёт `InputEvent::new(raw.keycode, raw.state)`. Конструктор в `crates/typetune-core/src/event.rs:18` устанавливает `character: None`. `LayoutManager` не вызывается ни источником, ни daemon; `with_character` не используется в runtime.

Corrector возвращает событие без анализа при `None` (`crates/typetune-corrector/src/lib.rs:187`), snippets делает то же (`crates/typetune-snippets/src/lib.rs:122`). Поэтому реальные буквы не попадают в их буферы. Double-Shift расположен до проверки `character`, но его buffer остаётся пустым; это не исправляет недостающий текст.

Это самостоятельная причина отсутствия функций поверх ошибок Linux keycodes. Подключить вызов `keycode_to_char` недостаточно: сразу станут достижимы повреждающие текст ошибки F09–F14. Требуется отдельный контракт физического ввода и подтверждённого текста.

### F02 — Reload сообщает успех без применения к pipeline (P1; S)

При старте daemon клонирует config (`crates/typetune-cli/src/main.rs:165`) и один раз строит стадии (`:185`–`:219`). SIGHUP (`:140`–`:144`) и D-Bus (`crates/typetune-cli/src/ipc.rs:42`) лишь заменяют значение в `Arc<Mutex<Config>>`. Callback продолжает использовать прежний pipeline (`main.rs:250`). Устройства, словари, debounce, snippets и logging не переинициализируются.

Одновременно `get_status` читает уже новый config (`ipc.rs:13`), поэтому список active features может стать ложным. Например, после сохранения `chatter.enabled=false` IPC перестанет перечислять anti-chatter, хотя его стадия останется активной.

Reload также всегда читает стандартный `config_path()`, даже если daemon запущен с `--config /other/file.toml`. Ошибка D-Bus reload только логируется, метод возвращает успешный пустой результат.

Нужен единый config controller: validate → prepare → безопасная граница событий → atomic apply → acknowledgement с номером применённой версии. Ошибка должна оставлять предыдущую working config и возвращаться вызывающему клиенту. Изменения, требующие restart/reopen, нужно явно классифицировать.

### F03 — Остановка не связана с event loop (P0 для готовности Linux; S, V)

Daemon регистрирует SIGTERM/SIGINT на собственном `Arc<AtomicBool>` (`main.rs:126`–`:129`). Этот флаг не передаётся в source и далее не читается. `EvdevSource` содержит другой флаг (`crates/typetune-input/src/lib.rs:114`), проверяемый своим циклом (`:196`). `source.stop()` из CLI не вызывается.

Следовательно, `typetune stop` отправляет SIGTERM, но предусмотренный кодом graceful stop не достигает source. Это делает непроверенными release grabbed devices, cleanup PID и остановку через systemd. Нужны единый cancellation token, пробуждение event loop и проверяемая последовательность drain/release/close.

### F04 — PID, custom config и готовность процесса расходятся (P1; S, V)

- Daemon/stop/status/reload используют `general.pid_file`, по умолчанию `/tmp/typetune.pid` (`config/default.toml:3`, `main.rs:116`, `:299`, `:324`, `:377`).
- `start_daemon` проверяет другой путь — `config_path().parent()/typetune.pid` (`main.rs:274`); tray Exit читает этот же другой путь (`crates/typetune-tray/src/lib.rs:98`). При default config Exit не находит PID daemon.
- Start запускает строку `typetune` из PATH и передаёт только `daemon` (`main.rs:287`). Не наследует пользовательский `--config` и не использует путь текущего executable.
- Через фиксированные 500 мс start печатает «Daemon started» независимо от того, завершился ли дочерний процесс с ошибкой (`:295`); вывод ошибок ребёнка направлен в null.
- PID-файл не заблокирован: последовательность read/check/write допускает два параллельных старта. Ошибки записи игнорируются (`:92`). `kill(pid, 0)` подтверждает лишь существование/доступность процесса, а не его принадлежность TypeTune; stale PID с повторно использованным номером может указывать на другой процесс.
- PID парсится как произвольный `i32` (`:103`) без проверки `pid > 0`; далее значение используется в `kill`. Для PID=0/отрицательных значений семантика системного вызова уже не «один daemon». Это дополнительная причина отказаться от неаутентифицированного общего PID-файла как командного канала.

Нужен один authority сервиса: локальный IPC и instance lock в runtime directory пользователя, readiness handshake и подтверждённое завершение. CLI должен возвращать ненулевой exit status при неудаче операции и показывать исходную причину.

### F05 — Конфигурация принимает неработающие настройки и плохо восстанавливается (P1/P2; S)

`crates/typetune-config/src/lib.rs` описывает типы и выполняет только TOML deserialization (`:68`). Нет semantic validation, schema version, migration и `serde(default)` для новых/опциональных полей. Неизвестные поля не отклоняются. Опечатка может игнорироваться, а отсутствие одного обязательного поля ломает загрузку всего файла.

Поля `corrector.layouts`, `exclude_classes`, `exclude_titles`, `snippets.word_separators` и `typography.*` нигде не применяются в runtime. Неизвестная строка `input.discovery` трактуется как ручной режим, потому что ветка проверяет лишь равенство `"auto"` (`main.rs:166`). Указанное пользователем значение не проверяется на поддерживаемость.

CLI загружает config до выполнения любой команды (`main.rs:55`–`:69`): повреждённый файл блокирует даже `version`, `config path`, `config edit` и `stop`. Создание конфига использует `unwrap` (`config/src/lib.rs:74`) и может завершиться panic при проблемах записи. GUI не создаёт default config, а падает, если его ещё нет (`crates/typetune-gui/src/main.rs:59`).

Установленный `/etc/typetune/config.toml` не служит обычным fallback: при наличии XDG config directory код создаёт пользовательский файл из compile-time `include_str!` (`config/src/lib.rs:78`). Изменённый администратором system config не наследуется. Приоритеты embedded/system/user/CLI нужно спроектировать явно.

### F06 — GUI сохраняет устаревший snapshot и не подтверждает применение (P2; S, V)

GUI умеет изменять только четыре флага (`gui/src/main.rs:164`–`:168`). Debounce, минимальная длина слова, списки исключений, devices, snippets и прочие настройки не редактируются. Save каждый раз клонирует config, прочитанный при открытии окна, и перезаписывает файл целиком (`:170`–`:180`). Внешние изменения после открытия окна будут затёрты; запись не атомарна.

Сохранение файла и reload daemon не составляют подтверждённую транзакцию: ошибка IPC игнорируется, пользовательского сообщения нет. Статус запрашивается один раз (`:77`) и не обновляется после Save/Reload. Синхронный `block_on` в UI callback (`:176`, `:193`) может блокировать окно на ожидании D-Bus.

Нужны версия конфига/защита от lost update, атомарная запись, асинхронный command client, видимые ошибки и отображение applied state. Редактор должен либо поддерживать поле, либо ясно оставлять его доступным через файл с сохранением чужих правок.

### F07 — Tray не соответствует заявленному управлению (P2; S, V)

В `crates/typetune-tray/src/lib.rs:39` меню содержит Enable/Disable, Reload config и Exit. Пункта Settings нет, хотя README обещает открытие настроек. Exit использует неверный PID path (F04). Toggle сначала меняет общий `enabled`, затем отдельно отправляет D-Bus команду (`:58`), что создаёт две точки управления одним состоянием и не сообщает об ошибках.

Нет подписки на изменения через IPC или явного обновления tray handle при внешнем изменении состояния; актуальность иконки/меню через внешний клиент требует отдельной live-проверки. В коде используются `input-keyboard`/`input-keyboard-disabled` (`:31`), а поставляются `typetune-active`/`typetune-disabled`; наличие disabled icon в конкретной теме не гарантируется.

Нужен tray как клиент одного controller, общий command contract с GUI/CLI и проверка поведения при отсутствии tray host. Отсутствие tray не должно мешать input service.

### F08 — Качество и происхождение словарей не подтверждены (P1 для корректора; S, R)

Проверено: каждый файл содержит 10 000 уникальных строк, однако `dict/en.txt` не содержит `hello`, `dict/ru.txt` не содержит `привет`. Поэтому примеры README не могут пройти dictionary gate даже после исправления transport. В русском файле встречаются `бежатьл`, `бежатьть`, `бежатьться`, а последняя строка — `사실`; в английском — `antiappear`, `antiatom`, `antibecause`. Это наблюдаемые признаки, а не доказательство истории генерации файлов: надёжный источник/метод построения в репозитории не установлен.

`Dictionary::load` подавляет любую ошибку чтения и создаёт пустой набор (`crates/typetune-corrector/src/dictionary.rs:9`). Строки приводятся к нижнему регистру без trim, нормализации или валидации языка. `is_valid_word` проверяет длину в UTF-8 bytes, а не число символов (`:24`), хотя минимальная длина word buffer в corrector считается иначе.

Нужны лицензия и происхождение ресурса, процедура обновления, нормализация и проверка содержимого, компактный обязательный regression corpus, оценка precision/false positives по языкам. При недоступном обязательном словаре capability корректора должна сообщать degraded/unavailable; пустой словарь не должен выглядеть успешной загрузкой.

## 4. Латентные ошибки после подключения текста

Эти сценарии **не означают**, что текущий Linux daemon уже выполнил описанные замены. Они достижимы через публичные API processor при `character: Some`, что воспроизведено безопасно в памяти. Их необходимо исправить до включения enrichment.

### F09 — Corrector одновременно удерживает ввод и удаляет уже введённое (P0 перед включением; S, R)

Буква добавляется в `word_buffer`, после чего возвращается пустой список (`corrector/src/lib.rs:192`). На разделителе успешная коррекция генерирует по Backspace на каждый накопленный символ (`:99`), хотя исходные буквы ещё не были отправлены приложению. В результате удаляются символы **до** текущего слова. При неуспешной коррекции все буквы выдаются только после разделителя (`:154`), что создаёт задержку отображения, а не обычное посимвольное редактирование.

Трасса с изолированным словарём `привет` и вводом `ghbdtn<space>`:

```text
g↓ h↓ b↓ d↓ t↓ n↓, каждый с character → [] для каждого Pressed
Space↓ → Backspace↓↑ × 6,
         key34↓↑ key35↓↑ key48↓↑ key32↓↑ key20↓↑ key49↓↑,
         Space↓
```

Система не ведёт единого учёта того, какие символы уже появились в приложении. Требуется выбрать семантику: наблюдать и заменять подтверждённый уже введённый диапазон либо подавлять ввод и владеть всем его воспроизведением. Для будущего текстового сервиса нужна первая модель с транзакцией replacement; смешивать модели нельзя.

### F10 — Нарушаются пары key down/up, регистр и семантика редактирования (P0/P1 перед включением; S, R)

Если `character` назначается только `Pressed`, matching `Released` проходит через `None` (`:187`) после подавленного `Pressed`: API выдаёт отпускание без нажатия. Если enrichment будет назначать `character` также отпусканиям, corrector и snippets добавят одну букву дважды: их текстовая ветка не фильтрует `KeyState`.

Буфер хранит только `char`: исходные modifier/device/selection/focus сведения отсутствуют в самой модели события. Небуквенные события без `character` (Backspace, Delete, стрелки, Ctrl-команды) проходят мимо буфера; его представление перестаёт соответствовать приложению. Buffer corrector не имеет лимита, а restart/disable/focus change не имеют согласованного reset.

Коррекция принудительно использует `to_lowercase` (`:72`, `:122`). Обратное преобразование `char_to_keycode` не нажимает Shift и возвращает одинаковый код для заглавных/строчных (`:221`). Ни corrector, ни output при этом не переключают целевую раскладку. Для `ghbdtn → привет` генерируются те же физические клавиши: под активной US-раскладкой они снова дадут `ghbdtn`. RU→EN символы `;`, `'`, `[`, `]` и другие отсутствуют в output mapping corrector и могут быть потеряны.

`is_word_char` признаёт только алфавитные символы; часть клавиш русских букв в ошибочной EN-раскладке является пунктуацией (`[`, `]`, `;`, `,`, `.`) и преждевременно завершает слово. `is_ascii` делит весь мир на EN/RU, поэтому другой алфавит/смешанное слово также ошибочно попадает в RU-ветку.

Нужны отдельные события committed text, editing commands, focus epoch, layout snapshot и provenance; Unicode insertion должен отвечать за текст, а не угадывать его по Linux keycode.

При срабатывании corrector исходное и исправленное слово пишутся в `tracing::info!` (`:97`, `:132`), а default log level — `info`. После подключения текста это станет записью пользовательского ввода в обычный журнал. Диагностика должна по умолчанию содержать только метаданные событий и результат операции; тестовый text trace допустим лишь в специально включённом режиме на синтетических данных.

### F11 — Double-Shift не имеет определённого жеста и истории (P1; S)

`corrector/src/lib.rs:173` проверяет только два Shift `Pressed` за `Instant::now` window. Нет обязательных Shift release, отсутствия промежуточных клавиш, отсутствия других modifiers или различия left/right. Обычный набор двух заглавных букв может выглядеть как жест. На срабатывании второй Shift press заменяется результатом `force_correct`, даже если buffer пуст (`:116`, `:181`).

После разделителя buffer очищается (`:207`), поэтому слово, завершённое пробелом, уже нельзя исправить. После ручной коррекции также нет undo/history. `reset` очищает buffer, но не `last_shift_press` (`:216`). Clock берётся из текущего времени обработки, а не события, что мешает детерминированному replay.

До разработки нужны примеры точного жеста, что значит «последнее слово», обработка trailing separator, запрет после cursor/focus/selection change, политика взаимодействия с системными shortcuts и сохранением регистра.

### F12 — Snippet удаляет на один символ больше и использует устаревший buffer (P0 перед включением; S, R)

`snippets/src/lib.rs:128` добавляет текущий символ перед matching. Если trigger найден, исходный текущий event **не** возвращается, но Backspace генерируется `trigger_len` раз (`:144`). Например, при trigger `:a` уже отображён только `:`, а последняя `a` перехвачена; два Backspace удалят ещё символ перед trigger.

Backspace/стрелки/смена фокуса не меняют buffer, а `SnippetExpander` не переопределяет `reset` вовсе. Проверено: `:a<Backspace>b` раскрывает `:ab`, хотя приложение содержит `:b`. Вызов `reset()` между `:a` и `b` не мешает тому же ошибочному раскрытию. После expansion buffer теряет trigger, но не отражает вставленный replacement. Границы `word_separators` игнорируются, boundary проверяется жёстким списком `:38` и означает только предыдущий символ.

Транзакция должна знать, доставлен ли последний символ trigger, и удалять лишь подтверждённый диапазон. Context tracker должен сбрасываться при потере достоверности, изменении focus/layout/selection, disable и после собственных изменений по явной политике.

### F13 — Renderer теряет Unicode/пунктуацию и блокирует input callback (P0/P1 перед включением; S, R)

`text_to_events` (`snippets/src/lib.rs:105`) молча пропускает символы без keycode. Mapping (`:162`) поддерживает ограниченный ASCII-набор без Shift. Проверено: replacement `A:Привет!` генерирует только key30 без Shift; `{{time}}` выдаёт шесть цифр без двоеточий.

Календарная формула (`:57`) использует годы по 365 дней и месяцы по 30 дней. Подстановка стабильных дат даёт `2024-02-29 → 2024-03-13`, `2026-09-10 → 2026-09-27`, `2026-12-31 → 2027-01-14`. Время (`:69`) вычисляется в UTC, без выбора locale/timezone. Дата и время запрашиваются отдельно и могут относиться к разным моментам.

Shell renderer вызывает `sh -c` и синхронно ждёт `.output()` (`:83`). Это происходит внутри pipeline callback (`main.rs:250`), который держит клавиатуры grabbed: зависшая команда останавливает пересылку дальнейшего ввода. Нет timeout, cancellation, ограничения stdout, проверки exit status и управления дочерней process group. Выход вновь ищется на `{{shell:...}}`, поэтому шаблон из вывода может повторно интерпретироваться как команда. Команды в данном аудите не запускались: эти риски установлены по control flow.

Нужны typed renderers, инъецируемые clock/timezone, одноразовый разбор шаблона, async worker с deadline/output limit/cancellation и явным разрешением command entries в пользовательской конфигурации. Worker должен работать с минимальными правами пользовательской сессии и не блокировать input transport. Результат нельзя вставлять в новое окно, если focus изменился во время ожидания.

### F14 — Последовательный pipeline не обеспечивает композицию функций (P1; S, R)

Corrector расположен до snippets (`main.rs:197`, `:217`). Он поглощает буквы trigger, затем создаёт новые `InputEvent::new` без `character`; snippets получает исходный `:` и разделитель, но не буквы `date`. Проверено: `:date<space>` при двух включённых стадиях выходит физическими клавишами исходного текста и не раскрывается.

Общее правило `Vec<InputEvent> → следующая стадия` (`core/src/pipeline.rs:23`) не определяет ownership текста, synthetic provenance, повторный matching и приоритет конфликтов. Даже после исправления отдельных алгоритмов это сохранит зависимость результата от порядка стадий.

Текстовые processors должны предлагать typed actions на одном согласованном context snapshot. Arbiter выбирает одну допустимую replacement transaction. Anti-chatter остаётся в физическом input слое; generated events не должны повторно выглядеть пользовательским trigger.

| ID | Вход / действие | Фактически подтверждено |
|---|---|---|

Данные фикстур: RU содержит только `привет`, EN — только `hello`; использовались события Pressed с `with_character` и keycodes evdev, поэтому результаты не зависят от плохого качества штатных словарей или текущей ошибки offsets.

## 5. Packaging и CI

### F15 — CI не проверяет поведение и не декларирует все native dependencies (P1/P2; S, V)

`.github/workflows/ci.yml:12` устанавливает evdev/udev/xkbcommon development packages, после чего выполняет workspace check. При этом workspace включает GTK4/libadwaita GUI и ksni, но workflow явно не устанавливает GTK4/libadwaita/D-Bus development packages. Наличие этих библиотек на конкретном `ubuntu-latest` runner в аудите не проверялось: текущая среда сборки не воспроизводима по одному workflow.

Есть только `cargo check`, Clippy и Fmt (`:13`–`:18`); нет `cargo test`, package build/install/uninstall, live input, матрицы ОС или заявленных desktop environments. Даже добавление `cargo test` без тестов не закроет проблему — сейчас их ноль.

Нужны отдельные jobs для переносимой логики, target-specific compile/lint, simulated event contracts и пакетов. Hardware/session acceptance выполняется отдельно с зафиксированным окружением и видео/trace результата, без записи реального пользовательского текста в логи.

### F16 — Наличие packaging файлов не подтверждает их включение и работоспособность (P1/P2; S, V)

`packaging/deb/postinst`, `prerm`, `conffiles` существуют, но в `crates/typetune-cli/Cargo.toml:30` не указана директория maintainer scripts; скрипты также не находятся среди assets. Нет явной связи metadata со скриптами и conffiles. Сам `.deb` не собирался/не распаковывался в аудите, поэтому нельзя заявлять ни включение scripts, ни окончательное содержимое пакета без `dpkg-deb --contents/--control`.

`Makefile:9` устанавливает файлы напрямую и не выполняет postinst. Документация предлагает input group, но в дереве packaging нет правила доступа к `/dev/uinput`; пользователь должен иметь и чтение input, и возможность создать output device. Это требуется проверить на чистой установке, не на подготовленной машине разработчика.

Postinst вызывает system-level `systemctl daemon-reload` (`packaging/deb/postinst:14`), хотя поставляется user unit. Prerm запускает `systemctl --user` из окружения package manager (`prerm:6`) без выбора пользовательской session/bus. Это не доказывает остановку daemon активного пользователя; upgrade/remove нуждается в отдельном контракте.

User unit жёстко задаёт `WAYLAND_DISPLAY=wayland-0` (`packaging/typetune.service:11`) и стартует через `default.target`, хотя зависимости относятся к graphical session. В текущем коде Wayland connection вообще не используется, поэтому hardcode не является установленной причиной нынешнего сбоя; при появлении session backend он станет неверным предположением о display. Переменные сессии должны приходить из реального окружения, а не из фиксированной машины.

Makefile `uninstall` удаляет `/etc/typetune` целиком (`Makefile:25`), включая возможные изменения администратора. Политика remove/purge и сохранения пользовательских данных должна быть явной. Debian dependencies по нижним версиям заданы вручную; соответствие фактически слинкованным native symbols требуется проверить на минимально поддерживаемой ОС.

## 6. Какие полезные наработки сохранять

- Разбиение на небольшие crates уже помогает изолированно собирать и проверять переносимую логику.
- Layout maps — полезные исходные таблицы физического RU/EN соответствия; после проверки punctuation/case они могут участвовать в чистом преобразовании текста.
- `Dictionary` как интерфейс membership и `Snippet` как исходная модель trigger/replacement подходят для переработки, но ресурсам нужны provenance и validation, а renderer — typed results.
- TOML/Serde model можно мигрировать с schema version и validation вместо полной смены формата.
- D-Bus interface, CLI commands и GUI/tray — заготовки пользовательских поверхностей. Их нужно подключить к одному controller, а не давать каждой поверхности менять разные копии состояния.
- Существующий pipeline полезен как прототип композиции; сохранять его контракт `physical event → Vec<physical event>` для всех текстовых функций нельзя.

Главная причина повторяющихся дефектов — отсутствие проверенного контракта между физическими клавишами, текстом приложения, конфигурацией и действующим состоянием сервиса. Добавление очередного обработчика в текущий pipeline увеличит число несовместимых предположений.

## 7. Минимальные acceptance contracts для новой реализации

### Текст и replacement

| ID | Проверка | Критерий приёмки |
|---|---|---|
| TXT-01 | EN/RU обычный набор, Shift, CapsLock, AltGr, удержание | Текст и shortcuts совпадают с выключенным сервисом; нет orphan down/up и дополнительной задержки до разделителя |
| TXT-02 | `PREFIX ghbdtn<space>` и обратное направление | Меняется только подтверждённое слово, `PREFIX ` сохранён, правильный язык и регистр |
| TXT-03 | Кириллица, emoji, combining marks, punctuation, multi-line snippet | Replacement совпадает с исходной Unicode-строкой; неподдерживаемый backend отказывается до удаления trigger |
| TXT-04 | Backspace/Delete/arrows/mouse/focus/layout change | Нет expansion/correction по устаревшему диапазону; подтверждённый context обновлён или сброшен |
| TXT-05 | Последний trigger character подавлен/уже доставлен | Число удалений соответствует доставленному диапазону; сохранён символ перед trigger |
| TXT-06 | Corrector и snippets включены одновременно | Приоритет документирован; trigger не теряется и не запускается повторно от synthetic output |
| TXT-07 | Double-Shift с interleaved typing/modifiers и после Space | Срабатывает только описанный жест, исправляет ровно предусмотренное слово и сохраняет парность клавиш |
| TXT-08 | Password/secure field, excluded app, неизвестный context | Поведение соответствует capability/policy; история из поля не переносится в другое приложение |
| TXT-09 | Undo, focus change во время replacement, partial insertion failure | Нет слепого retry/backspacing в новом контексте; результат операции и границы восстановления известны |

### Renderers и ресурсы

| ID | Проверка | Критерий приёмки |
|---|---|---|
| RND-01 | Leap day, смена года/суток, timezone | Стандартная библиотека календаря, один snapshot clock, ожидаемые date/time строки |
| RND-02 | Worker timeout/cancel/nonzero exit/огромный output | Ввод продолжает работать; ограничены время/память, дочерние процессы завершены, видна ошибка |
| RND-03 | Command output содержит шаблонные скобки | Output трактуется как текст, не как новая инструкция к renderer |
| RND-04 | Словарь отсутствует/повреждён/не той версии | Явная ошибка capability, предыдущий рабочий ресурс сохранён; успешная загрузка не симулируется |
| RND-05 | Размеченный RU/EN corpus и отрицательные случаи | Измерены precision/recall; README examples входят в обязательный набор; false positives ограничены заранее выбранным порогом |

### Lifecycle, конфигурация и поставка

| ID | Проверка | Критерий приёмки |
|---|---|---|
| CTL-01 | Reload каждого поддержанного поля через CLI/GUI/IPC | Меняется effective behavior, applied revision одинакова у всех клиентов |
| CTL-02 | Невалидный/частичный config, неизвестное поле | Ошибка с указанием поля; last-known-good остаётся активным, команды диагностики доступны |
| CTL-03 | Custom config, два simultaneous starts, stale PID | Одна instance, правильный путь конфигурации, никакой сигнал постороннему процессу |
| CTL-04 | SIGTERM/SIGINT/GUI Exit/systemd stop | Подтверждённое завершение, release output key state, ungrab/close, cleanup instance lock |
| CTL-05 | Disable/enable с непустым text state | Устаревший buffer не используется; mode transition не оставляет зажатых клавиш |
| CTL-06 | GUI Save одновременно с внешним edit | Конфликт или merge без потери данных; atomic write; error и applied state видны |
| PKG-01 | Чистая установка поддержанной ОС | Права минимально необходимы; вход и output доступны, запуск без ручных скрытых шагов |
| PKG-02 | Upgrade/remove/purge при активной сессии | Сервис корректно остановлен, клавиатура доступна, user data сохранены согласно политике |
| PKG-03 | Нет session bus/tray host/graphical session | Предсказуемый degraded state; transport не зависит от успешного запуска UI |
| PKG-04 | Артефакт из CI на минимальной версии ОС | Проверены assets, native dependencies, scripts, service и config migration |

Каждый реализуемый пункт должен иметь автоматический contract test там, где возможна детерминированная модель, и live acceptance на заявленном backend там, где результат зависит от приложения, compositor или permissions. Отчёт обязан отличать «собралось», «прошло модель» и «работает на конкретной ОС/сессии».
