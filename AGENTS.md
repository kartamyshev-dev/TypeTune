# TypeTune: работа с проектом

## Контекст и источник истины

- Отвечать пользователю по-русски; результат, проверки и ограничения разделять явно.
- Текущая отправная точка — Linux-прототип. Не объявлять функции/платформы работающими по наличию исходников.
- До существенной реализации прочитать `docs/00-overview.md`, `docs/13-target-architecture.md`, нужные разделы `docs/14-development-plan.md` и `docs/16-product-spec.md`.
- `docs/11-linux-audit.md` и `docs/12-feature-audit.md` описывают дефекты baseline `8cc19d0`; сверять их с текущим кодом. `docs/archive/initial-plan/` — история, не инструкция.
- Канонические решения и checkpoint хранить в документации проекта. Сохранять незавершённые правки пользователя и других задач.

## Контракты реализации

- Разделять физическую фильтрацию и семантическую работу с текстом. Shell, сеть, GUI и renderer не должны блокировать physical forwarding/hook callback.
- Не смешивать native keycode spaces; offset evdev/XKB применяется только на соответствующей границе. Сохранять Down/Up/Repeat, source time, device identity и origin.
- Обычный текст сразу получает приложение. Правила предлагают планы замены; один исполнитель отвечает за удаление, Unicode, modifiers, focus/context guards и результат.
- `Unknown` capability/context не трактовать как успешную проверку. X11, XWayland и native Wayland профили проверять отдельно.
- Before-edit отказ сохраняет исходный текст; after-edit неопределённый результат не запускает слепой retry. Не обещать атомарность замены без соответствующего API.
- Доступ к Linux devices и владение grab изолировать от text engine. Shutdown, output failure, resync, hotplug и watchdog входят в обязательный контракт.
- Изменение настройки должно менять effective state либо явно возвращать ошибку/restart-required. GUI/CLI/IPC используют один controller.

## Проверки и готовность

- Сначала воспроизвести дефект trace/test, затем менять соответствующий слой. Не подгонять keycode offset по видимому символу без проверки границ.
- Для изменений поведения добавить meaningful regression tests; для чистой документации проверить ссылки, согласованность и diff.
- Использовать fake clock и контролируемый editor для deterministic тестов. Проверять содержимое/каретку и состояние клавиш, а не только успешный вызов API.
- Компиляция, simulated tests и native acceptance — разные результаты. `0 tests` не считать проверкой поведения.
- Не запускать непроверенный exclusive grab на основной клавиатуре. Live стенд должен иметь выбранное тестовое устройство, готовый output, независимую остановку и проверку восстановления.
- Указывать commit, ОС, session/backend, версии desktop/app, IDs выполненных cases и оставшиеся ограничения. Не записывать пользовательский текст/clipboard в обычные логи и артефакты.
- Не копировать код Espanso без отдельной проверки происхождения и условий использования; reference с pinned links находится в `docs/15-espanso-reference.md`.
